# 校园聚合平台 全量审查方案 v3

<!-- 制定日期: 2026-05-25 | 团队讨论: AgentA/B/C 三线评审后合成 -->

> **这是校园聚合平台项目的标准审查流程。所有后续功能审查、问题排查、验收测试均须按此流程执行。**

---

## 流程总览

```
阶段0: 原型→规范（60min）
  ↓
阶段0.5: 共享层集中审查（30min）
  ↓
阶段1.5: 快速烟雾测试（30min）
  ↓
阶段2: 分层并行审查（3-5h）
  ↓
阶段3: 汇总+去重+交叉验证（1h）
  ↓
阶段4: 修复（按优先级分批）
```

## 阶段0: 原型→规范（60min）

### 0.0 机器解析HTML（脚本，5min）
- 用Python/Node脚本解析原型HTML
- 产出 `parsed-data.json`：包含所有Screen的DOM树、CSS计算值、交互行为、导航关系
- 验收：34个Screen全部解析，CSS变量100%提取，隐含颜色全部列出

### 0.1 全局Design Token提取（1 Agent，15min）
- 输入：`parsed-data.json`
- 产出 `design-tokens.md`：Color/Typography/Spacing/Shape/Shadow/Gradient 六大类Token
- 关键：隐含Token（不在CSS变量中的硬编码值）必须显式命名
- 每个Token标注Material3 Compose映射

### 0.2 Screen规范（5 Agent并行，20min）
- 按业务模块分5组，每组6-9屏
- 产出 `screen-{name}.md`：
  - 布局结构树（ASCII art）
  - 逐元素规范表（CSS属性 → Token引用 → M3 Compose等价）
  - 交互行为表（触发 → 目标 → 行为类型）
  - 状态变体表（状态名 → 影响元素 → CSS变化）

### 0.3 跨Screen交叉校验（1 Agent，10min）
- 检查：Token一致性、组件一致性、交互完整性、隐含Token逃逸、M3映射合理性
- 产出 `spec-issues.md`：按P0/P1/P2分级的问题清单
- AgentX-1~5 根据issues修正各自的规范文件

### 0.4 生成Android对照清单（1 Agent，10min）
- 产出 `android-implementation-checklist.md`
- 格式：逐条规范 → Compose实现 → 打勾状态
- 必须包含明确的反模式标注（如"不是FilterChip，是Column+定宽左侧栏"）

## 阶段0.5: 共享层集中审查（30min）

**目的：防止跨Screen边界遗漏。**

1个Agent审查所有跨Screen公共模块：
- 组件库（RunnerTaskCard/MarketFeedCard/LostItemCard 等）
- 导航/路由一致性
- 状态管理/DI
- API层（Repository/Supabase调用）
- 权限控制/RLS

## 阶段1.5: 快速烟雾测试（30min）

**目的：在投入深度审查前确认基础环境可用。**

1. 环境检查（5min）
   - adb确认模拟器连接
   - adb install确认App可安装
   - curl确认Supabase端点可达

2. 启动链路（10min）
   - 启动App → 5秒后检查进程存在 → logcat确认无FATAL → 截屏确认非白屏

3. 跳过OTP的登录（5min）
   - 通过Supabase Admin API生成access_token
   - 写入App DataStore
   - 重启App进入主界面

4. 核心链路遍历（10min）
   - adb点击5个主导航Tab
   - 每个停留3秒后截屏
   - 检查logcat无ERROR级日志

**通过标准：所有核心页面可导航到、无崩溃、无ANR、Supabase连接成功。**

## 阶段2: 分层并行审查（3-5h）

### Layer B: 按Screen均分（6 Agent并行）
- 每人6-8个Screen
- 每屏检查：
  - UI对照清单（对照阶段0.4的Android对照清单）
  - ViewModel调用链（每个public方法是否被Screen调用？init{}是否触发加载？）
  - 四态处理（Loading/Empty/Error/Success是否都有处理？）
  - 导航闭环（每个onClick→目标路由是否注册？参数是否正确？返回键是否正确？）
- **强制要求：每个"不通过"必须附代码位置+adb截图证据。无证据的"通过"视为无效。**

### Layer C: 跨模块横向审查（2 Agent并行）
- C1: 路由/导航/数据流一致性
- C2: 权限/安全/数据一致性

### 质量保障机制
- **审查清单强制绑定**：每份审查报告必须附结构化checklist（每个检查项：通过/不通过/不适用）
- **三级共享机制**：
  - L1: Agent发现可能是系统性问题的，立即写入共享板
  - L2: 阶段2结束后汇总去重
  - L3: 阶段4由1个Agent统一合并

## 阶段3: 汇总+去重+交叉验证（1h）

### 3.1 去重+分类
- 汇总Layer B + Layer C所有发现
- 去重
- 标记"系统性问题"（≥3个Screen共有的问题）

### 3.2 交叉抽样验证
- 随机抽取10%审查结果
- 由另一Agent独立重新审查
- 结论一致的通过/不通过算有效
- 不一致的标记为"需人工判定"

### 3.3 高风险Screen专项复查
- 选取标准：变更行数>200 / 发现数>15 / 核心流程Screen
- 选Top 6-8个Screen，2 Agent各负责3-4个
- 复查重点：修复是否引入新问题

### 3.4 跨模块边界测试
- 选取5-8条关键用户路径（如"注册→选校→发布跑腿→接单→完成→评价"）
- 1个Agent走查完整路径，检查数据传递和状态一致性

## 阶段4: 修复（按优先级分批）

### 优先级定义
| 级别 | 定义 | 例子 |
|:--:|------|------|
| P0 | 阻塞级：不改无法使用 | 编译失败、启动崩溃、核心链路断裂 |
| P1 | 严重：功能缺失或数据错误 | 页面无数据、数据不一致、UI与原型严重不符 |
| P2 | 建议：体验问题 | 动画缺失、样式偏差、缺少空态引导 |
| P3 | 锦上添花 | 性能优化、代码整洁 |

### 修复流程
- P0 → 立即修，修完重新烟雾测试
- P1 → 分批修，每批修完交叉验证
- P2 → 统一修，修完抽查
- P3 → 排期修，不阻塞发布

## 核心原则

1. **审查前先有规范**：对照原型逐元素清单，不是"感觉像不像"
2. **分工均衡**：按Screen数均分，不是按模块名
3. **证据驱动**：每个"不通过"必须有代码位置+截图
4. **先跑通再深入**：烟雾测试不通过，不进入深度审查
5. **共享层先审**：公共组件/路由/状态单独审查，不被Screen均分掩盖
