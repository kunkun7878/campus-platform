# 15-可审计证据机制.md

> 目标：为前期 UI 多 Agent 协作建立一套可审计证据体系，使用户可以验证任务是否真实分发、真实执行、真实审查、真实打回、真实复审。

---

## 1. 可审计证据的基本原则

### 1.1 证据优先于口头说明
任何关于“已完成、已调用、已审查、已修复、已通过”的表述，都必须能映射到明确证据。

### 1.2 证据必须可定位
证据不能只是概念描述，必须能定位到：
- 任务编号
- 文档位置
- 会话记录
- 审查编号
- 打回编号

### 1.3 证据必须可串联
用户应能从一个任务编号追到：
任务登记 -> 子 Agent 产物 -> 审查记录 -> 打回记录 -> 复审记录 -> 合并结论

---

## 2. 证据类型

### 2.1 任务登记证据
证明任务是否真实创建与派发。

字段要求：
- 任务编号
- 任务名称
- 指派对象
- 指派时间
- 输入来源
- 输出要求
- 当前状态

### 2.2 执行产物证据
证明执行 Agent 是否真实工作。

字段要求：
- 任务编号
- 执行 Agent 名称
- 产物名称
- 产物时间
- 产物位置
- 自检状态

### 2.3 审查证据
证明审查是否真实独立发生。

字段要求：
- 审查编号
- 任务编号
- 审查 Agent 名称
- 审查结论
- 是否允许合并
- 问题项

### 2.4 打回证据
证明返工是否真实发生。

字段要求：
- 打回编号
- 原任务编号
- 打回原因
- 修复要求
- 复审要求

### 2.5 复审证据
证明修复后是否真实复核。

字段要求：
- 复审编号
- 对应打回编号
- 复审结论
- 仍未解决项

### 2.6 合并证据
证明主智能体不是直接口头宣布完成，而是基于通过项进行正式收口。

字段要求：
- 合并批次编号
- 合并任务列表
- 未合并原因列表
- 当前风险项
- 汇报时间

---

## 3. 最低可审计要求

如果要宣称“本轮已完成多 Agent 协作”，至少必须具备：

1. 任务登记证据
2. 至少一个子 Agent 独立产物
3. 至少一个独立审查记录
4. 如有返工，则必须有打回与复审记录
5. 主智能体汇报证据摘要

少任意一项，则不能宣称“协作流程完整成立”。

---

## 4. 用户抽查路径

用户可按以下方式抽查：

### 路径 A：从任务编号抽查
查看：
- 原始任务包
- 指派对象
- 独立产物
- 审查记录
- 最终状态

### 路径 B：从审查编号抽查
查看：
- 被审任务
- 审查原文
- 是否有对应修复
- 是否有复审结论

### 路径 C：从汇报结论反查
查看：
- 本轮声称调用了哪些 Agent
- 这些 Agent 的真实产物在哪里
- 哪些任务通过了
- 哪些任务被打回了

---

## 5. 证据缺失时的降级规则

如果主智能体无法提供对应证据，则结论自动降级：

- “已由多 Agent 完成” -> 降级为“未验证的主智能体陈述”
- “已审查通过” -> 降级为“无独立审查证据”
- “已修复完成” -> 降级为“无复审证据”
- “本轮已收口” -> 降级为“无合并证据”

这条规则的作用，是防止没有证据时还继续沿用高置信表述。

---

## 6. 当前结论

可审计证据机制的核心不是“多存一些文件”，而是把每一个关键动作都变成可检查、可反查、可串联的记录。

对于前期 UI 多 Agent 协作系统，证据链越完整，主智能体越难假装协作、假装审查、假装打回，用户对系统的控制力也越强。
