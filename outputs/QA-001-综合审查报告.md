## 三、严重度校准

### 3.1 校准原则

统一采用三级严重度：
- 🔴 **致命**：阻断核心流程、违反硬规则、无此功能则原型无意义
- 🟡 **严重**：影响主流程体验/数据完整性/可维护性/可开发性
- 🟢 **建议**：优化方向、锦上添花

### 3.2 需要校准的问题

| 问题 | 原报告评级 | 校准后评级 | 校准理由 |
|------|:--------:|:--------:|---------|
| **搜索功能不可用** | EXEC-002 🔴 / EXEC-001 🟢 | 🔴 **致命** | 搜索是产品核心功能入口，完全不可用属阻断性缺陷。EXEC-001 将其归为🟢偏低 |

## 四、综合优先级排序

### 4.1 分级标准

| 等级 | 定义 | 判定依据 |
|:---:|------|---------|
| **P0** | 原型硬伤、核心规则不达标、阻断性功能缺失 | 不修原型就无评审意义；核心流程完全不可走通 |
| **P1** | 影响主流程闭环、关键体验缺陷 | 不修体验差，影响主要场景可用性 |
| **P2** | 辅助功能缺失、可维护性/可开发性缺陷 | 影响但可暂缓，不影响核心流程演示 |
| **P3** | 锦上添花、美化优化、技术债 | 可在后续迭代中处理 |

## 五、遗漏检查

### 5.1 检查方法

逐行审阅原型本体 `campus-miniapp-prototype.html`（共 1425 行 HTML + CSS + JS），对照三份报告的全部发现，识别遗漏项。

### 5.2 发现的遗漏问题

| # | 遗漏问题 | 严重度 | 证据 | 遗漏原因分析 |
|---|---------|:-----:|------|------------|
| **MISS-1** | **`.content` + `.screen` 均设置 `overflow: hidden`，12/14 screen 无可滚动容器** | 🔴 致命 | CSS: `.content { height: calc(920px - 170px); overflow: hidden; }`（L188）；`.screen { height: 100%; overflow: hidden; }`（L195）；仅 `#screen-home` 的 `.runner-scroll` 和 `#screen-profile` 的 `.profile-scroll` 有 `overflow-y: auto`。其余 12 个 screen（publish、publish-hub、order-detail、order-list、after-sale-apply、after-sale-detail、goods-detail、lost-detail、lost-claim、community、message、announcement-detail）在内容超出可视区域时**被静默裁剪，用户无法滚动查看完整内容**。publish 表单包含 8+ 个字段 + 图片按钮，大概率超出。 | 三份报告均侧重"状态缺失"和"组件缺失"，但未检查所有 screen 的基础滚动可行性。EXEC-002 提到 `.content` 高度硬编码（GS1）但仅从响应式角度，未发现 overflow clip 问题 |
| **MISS-2** | **`screenConfigs` 中 `nav` 属性映射不一致** | 🟡 严重 | JS `screenConfigs`（L1378–1392）：`order-detail`、`order-list`、`after-sale-apply`、`after-sale-detail` 的 `nav` 均为 `'profile'`，即这些页面激活时底部导航高亮「我的」。但 order-detail 是从 homepage feed-card 进入的，order-list 可能是从 publish 页或个人中心进入的——将底部导航「我的」高亮与这些页面的语义归属不一致。用户从首页点跑腿卡片进入订单详情后，底部导航却高亮「我的」。 | EXEC-002 分析了 historyStack 行为，但未检查 screenConfigs 的 nav 映射语义正确性 |
| **MISS-3** | **`screenConfigs` 中所有 screen 的 `hero` 均为 `true`，hero 区域无差异化** | 🟡 严重 | JS L1378–1392：14 个 screen 全部 `hero: true`。非首页 screen 既显示 hero（含状态栏模拟 + brand + search bar），又有自己的 `page-top`（含标题 + back-btn），形成双重标题区。各 screen 的具体内容被 hero + page-top 压缩后，实际可用内容高度大幅缩减。 | EXEC-002 GH5 提到了 hero 与 page-top 的视觉冗余，但未系统指出所有 screen 的 hero 无差异化配置问题 |
| **MISS-4** | **「退出登录」按钮完全不可用**（仅纯展示） | 🟡 严重 | HTML L1346：`<button class="logout-btn" type="button">⏻ 退出登录</button>` — 无 `data-screen-target`、无 JS 事件绑定、无任何 id/class hook。点击完全无响应。STRUCT-001 提到需要 Modal 做退出确认（§3.2），EXEC-002 P4 也提到需要确认弹窗——但两份报告均未明确指出现有按钮**完全不可用**（不仅仅是缺二次确认）。 | 报告侧重于缺乏"确认弹窗"而非指出按钮本身不可用 |
| **MISS-5** | **「申请售后」→ after-sale-apply 链路无订单上下文传递** | 🟡 严重 | HTML L388: `data-screen-target="after-sale-apply"` 从 order-detail 跳转到售后申请页，但无 `data-order-id` 等参数。after-sale-apply 表单中不展示关联订单信息，用户无法确认"对哪个订单申请售后"。同样，after-sale-detail 也未从 after-sale-apply 接收提交上下文。 | EXEC-001 4.3 提到了订单号硬编码和 screen 之间未关联，但措辞较轻，未将其提升为"链路缺失"级 |
| **MISS-6** | **`announcement-marquee` 动画依赖双倍内容复制，非标准可维护方案** | 🟢 建议 | HTML L302–309：公告区 marquee 动画通过在 HTML 中复制完全相同的两段 `<strong>…<span>…</span></strong>…<span>…</span>` 来实现无限循环滚动效果。这导致 DOM 冗余，维护时需要同步修改两处，且无 JS 动态控制。 | 纯实现细节，三份报告均从产品/交互角度审查，未关注此实现细节 |
